# MTR Tracker

Continuous MTR monitoring for IT professionals: a FastAPI + PostgreSQL backend runs `mtr --json` against user-defined targets on a schedule, stores every hop of every run, and a React UI visualises latency, loss, jitter, per-hop history and route changes.

## Layout

```
backend/app/        Python package (run with `python -m uvicorn app.main:app` from backend/)
  main.py           FastAPI app factory, lifespan (DB + scheduler), SPA static serving
  api.py            All HTTP routes under /api
  scheduler.py      24/7 loop: due targets -> run -> store -> classify -> events/webhooks; retention purge
  mtr.py            mtr command builder, JSON parser, route signature/compare, simulator
  probes.py         ping / http / tcp / dns probes -> ProbeOutcome (same summary shape as an MTR run + details dict)
  globalping.py     Globalping API client (globalping.io): remote ping/dns/http -> ProbeOutcome, remote mtr/traceroute -> MtrResult with hops
  geoip.py          GeoIP providers: MaxMind GeoLite2 City + ASN (download with the saved licence key, cached lookups), ip-api.com first when switched on, path_geo() for the map
  ipapi.py          ip-api.com client: batched POST /batch lookups (100 per request), local request budget below the service's limit, X-Rl/X-Ttl handling, failure pause, cache
  notify.py         Notification channels (webhook, Pushover); dispatch_event fans one payload out to all enabled channels, wanted() says whether any channel takes a kind
  cooldown.py       NotifyGate: per-target notification cooldown (settings.notify_cooldown_min), held-back alerts and the catch-up
  resolver.py       forward DNS and reverse DNS with a TTL cache
  db.py             PostgreSQL schema (targets, runs, hops, events, settings), asyncpg pool, transaction() helper, batched retention purge
  migrate.py        One-time import of a legacy SQLite file: automatic at start while PostgreSQL is empty, or python -m app.migrate
  models.py         Pydantic request schemas

backend/tests/      pytest (asyncio mode auto); fixtures in conftest.py (client, protected_client, static_client) built by helpers.app_client, which runs the app in simulation mode against a PostgreSQL database dropped and recreated per test (MTR_TRACKER_TEST_DATABASE_URL; app tests skip without a server, fail in CI); test_migrate.py seeds legacy SQLite files

  pages/            Dashboard, TargetDetail, RunView, Events, Settings, QuickTrace, GeoLookup (one address against GeoLite2, with the map marker)
  components/       Charts (RTT/loss/jitter + Sized wrapper), Visuals (overview, path profile, histogram, hourly heatmap, route timeline), StatusStrip, HopHeatmap, HopTable, PathSummary, PathMapCard (map card, buildStops) + PathMap (Leaflet, lazy), RunsTable, EventsList, TargetForm, TargetActions, Popover (HelpTip/ActionMenu), Tabs, Tags (colour provider, chips, colour picker), TagPicker (TagSelect/TagMenu/TagEditor), TagFilter (dashboard filter), GroupPicker (GroupSelect/GroupMenu), TypeBadge, Pager, Layout
frontend/tests/     Vitest + jsdom + Testing Library component tests; setup.ts isolates localStorage, mocks ResizeObserver and rejects unexpected fetch calls
```

## Commands

```bash
# Run each section from the repository root; backend and frontend servers use separate terminals.
# Backend (Python 3.11+; CI/Docker use 3.12). Needs PostgreSQL 13+: `docker compose up -d db` (published
# on 127.0.0.1:5432), or `docker run --rm -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16-alpine`.
cd backend && pip install -r requirements-dev.txt
MTR_TRACKER_SIMULATE=1 MTR_TRACKER_DATA_DIR=./data MTR_TRACKER_DATABASE_URL=postgresql://mtr:mtr@127.0.0.1:5432/mtr_tracker python -m uvicorn app.main:app --reload --port 8899
MTR_TRACKER_TEST_DATABASE_URL=postgresql://mtr:mtr@127.0.0.1:5432/mtr_tracker python -m pytest -q   # the compose db; a role that may CREATE DATABASE. The docker run server takes postgres:postgres@127.0.0.1:5432/postgres on both lines
python -m app.migrate --sqlite ./data/mtr-tracker.db   # import a legacy SQLite file by hand (--replace, --all, --rename)

# Frontend (Node 22.22.2+ in the 22.x line, required by the locked jsdom version)
cd frontend && npm ci
npm run dev          # Vite on :5173, proxies /api to :8899
npm run build        # tsc --noEmit && vite build -> frontend/dist (served by the backend if present)
npm run typecheck    # TypeScript check without emitting a build
npm test             # Vitest component tests; no running backend needed

# Docker
docker compose up -d --build
```

## Conventions and gotchas

- **Naming**: the product is "MTR Tracker". Identifiers use `mtr-tracker` (logger names, image, volume) and env vars use the `MTR_TRACKER_` prefix. Do not reintroduce other names.
- **Config is import-time**: `config.py` builds a frozen `Config` when imported. Tests that change env vars reload `config`, `mtr`, `probes`, `globalping`, `geoip`, `scheduler`, `api` and `main` (see `tests/helpers.py`); any new module that imports `config` must join that list. `db.py` and `migrate.py` deliberately do not import it (`main.py` passes the values in; the migrate CLI reads the environment itself, so `--help` never creates the data directory; `DEFAULT_DATABASE_URL` lives in `db.py`).
- **mtr is always run with `-n`** (numeric). The app resolves the host itself before the run so the destination hop can be matched by IP, and does reverse DNS afterwards with a cache. Do not pass hostnames to mtr.
- **Simulation mode** (`MTR_TRACKER_SIMULATE=1`) produces synthetic probe results; local MTR paths are seeded by the destination /24. Missing mtr or ping binaries trigger fallback only for their respective probe types. Hostname resolution for local MTR/ping/TCP, reverse DNS for local MTR and enabled notifications can still access the network. For isolated UI work, use IP-literal targets, disable reverse DNS and leave notification channels disabled.
- **Timestamps** are stored as epoch floats (DOUBLE PRECISION) and serialised as ISO 8601 UTC strings with a `Z` suffix in the API.
- **Probe types**: `targets.type` is `mtr | ping | http | tcp | dns | globalping`; type-specific settings live in `targets.options` (JSON) validated by the `*Options` models in `models.py` (`validate_options`). Summary runs have `hop_count = 0`, no hop rows, and a `runs.details` JSON blob rendered by `CheckDetails.tsx`. The UI decides on path panels with `isPathProbe(type, options)` and on loss semantics with `isPacketProbe(type, options)`, because a Globalping target is a path probe only when its `measurement` is `mtr` or `traceroute`. Adding a type: runner in `probes.py` (+ `RUNNERS`; `run_probe(t, settings)` also receives the settings), options model, `DEFAULT_OPTIONS`/`PROBE_TYPE_LABEL`/`LATENCY_ALERT_DEFAULT` in `api.ts`, form fields in `TargetForm.tsx`, details rendering.
- **Globalping** (`globalping.py`) supports all five API measurements. `build_request` maps the target (`count` = packets for ping/mtr, max 16; `protocol`/`port`/`ip_version` for mtr/traceroute; `port` for http) and its options (`measurement`, `location` as the API's "magic" field, `probes`; dns: `record_type`/`resolver`/`expected`/`dns_transport`; http: `path`/`http_method`/`http_protocol`/`expected_status`/`keyword`, a pasted URL is split by `http_target`) to `POST /v1/measurements`; `measure()` polls until finished and raises `GlobalpingError` (rate limit, no probes, validation, timeout). `PATH_MEASUREMENTS` (mtr, traceroute) become an `MtrResult` (hops via `hop_from_result` / `hop_from_traceroute`, `src` = probe label, `details.probe`) that the scheduler runs through `_execute_path` with `local_names=False` (the probe's hostnames are kept); ping becomes a packet-based `ProbeOutcome` (`_ping_outcome`); dns and http are per-probe checks folded by `_check_outcome` (down when no probe passed, a warning and therefore degraded when only some did), with `details.probes[]`, `details.answers`/`rcode` for dns and `details.request`/`status`/`timings`/`tls` for http (`tls_info_from_result` maps the API's tls block to the same shape as the local probe's `details.tls`). The optional `settings.globalping_token` is a masked secret. Simulation mode fabricates probes without calling the API; tests use `globalping._FORCE_LIVE` + `globalping._TRANSPORT` (MockTransport). The UI derives path/packet semantics from `isPathProbe`/`isPacketProbe`/`latencyLabel` in `utils.ts`, all of which take the options.
- **GeoIP providers** (`geoip.py`, `ipapi.py`): two providers, selected per lookup. `settings.ip_api_enabled` (boolean, default off) asks ip-api.com first; `settings.maxmind_license_key` enables the GeoLite2 databases, which answer whatever ip-api.com cannot (address not placed, not answered yet, or the service paused after a failure). `configured(settings)` is true with either, `maxmind_configured(settings)` only with the key; `available(settings)`/`asn_available(settings)` say whether any provider can answer now and take the settings. `path_geo` and `lookup_query` first `await _prefetch(ips, settings)`, which calls `ipapi.prefetch()` with every public address of the run (monitor or its cached `public_ip()`, hops, destination) so one batched request answers a whole path; `lookup(ip, settings)`, `locate`, `network` and `_network_fields` then consult `ipapi.get(ip)` before the databases and are never called with settings from the simulator (`_ip_api_on` is false in simulation, so no network call is made). `ipapi.py` posts up to `BATCH_SIZE` (100) addresses per request to `http://ip-api.com/batch?fields=…` (the free tier has no TLS), spends at most `MAX_REQUESTS_PER_MINUTE` (6) requests per rolling minute against the service's limit of 15 and never waits for the budget (an address that does not fit is left to MaxMind and asked on the next poll), honours `X-Rl: 0` by pausing for `X-Ttl`, and after any failure (transport error, HTTP 429 with its `X-Ttl`, other status, unreadable body) pauses for `FAILURE_BACKOFF` (5 min); `ready()` is false while paused, `wake()` (called by `PUT /api/settings` when `ip_api_enabled` changes) ends a pause, `reset()` clears everything for tests. Answers are cached for `CACHE_TTL` (6 h, also for addresses the service could not place; unanswered ones for 5 min). `parse_result()` maps an entry to the same `geo` shape as `parse_record()` (`accuracy_km` is null, the service states none) plus `network` from the `as` field ("AS15169 Google LLC"; `asname` when `as` carries only the number). Every `geo` dict names its `provider` (`ip-api.com`, `GeoLite2`, `Globalping`, `simulated`). Missing-location notes gained `ip-api.com unavailable` (paused, no database) and `lookup pending` (budget spent, no database). `GET /api/geoip/status` keeps `configured`/`available`/`asn_available` as the MaxMind facts and adds `ip_api` (`enabled`, `simulated`, `ready`, `paused_until`, `pause_reason`, `last_attempt`, `last_success`, `last_error`, `requests_last_minute`, `max_requests_per_minute`, `batch_size`, `requests_total`, `addresses_total`, `cached`); the geo endpoint adds `ip_api_enabled`; the lookup endpoint adds `ip_api_enabled`, `ip_api_ready` and `maxmind_configured` and its `configured`/`available` mean any provider; its `provider` query (`PROVIDERS` = `auto` | `ip-api` | `maxmind`, echoed in the response) picks the backend: `lookup_query` passes the choice as the private `_provider` key of the settings it hands down, `_ip_api_on` is true for `ip-api` even with the switch off, `_maxmind_on` is false for `ip-api` (never in simulation), so `lookup`, `network`, `available`, `asn_available` and `_missing_note` honour it without new parameters. The page offers it as the **Provider** radiogroup (`GEO_PROVIDER_LABEL` in `api.ts`) and repeats the lookup when it changes. Tests inject `ipapi._TRANSPORT` (MockTransport) next to `geoip._TRANSPORT` and call `ipapi.reset()`. Frontend: the **ip-api.com GeoIP** section in Settings (checkbox "Enabled", `aria-label` "Use ip-api.com", status line `ip-api-status`) sits above **MaxMind GeoIP**; `PathMapCard`, the GeoIP lookup page ("Source" row) and the map footer word the provider from `ip_api_enabled`/`geo.provider`.
- **GeoIP map** (`geoip.py`): `settings.maxmind_license_key` (masked secret) enables the databases; `maxmind_account_id` is optional and switches the download from the legacy `geoip_download?license_key=` URL to the basic-auth permalink. Two editions are downloaded with the same credentials, `EDITIONS` = GeoLite2 City (places) and GeoLite2 ASN (network names); each `.mmdb` lives at `config.data_dir/geoip/<edition>.mmdb` (never in the repo or image), is verified (`_verify` checks the edition's type) before an atomic `os.replace`, and `schedule_refresh()` re-downloads them when either is missing or older than `REFRESH_AFTER` (7 days) from the scheduler's cleanup tick and after a settings save. `download()` fetches City first and then ASN; an error names the edition (`GeoLite2-ASN: …`) and a failed ASN download leaves the fresh City database in place. `reader(edition)` keeps one open reader per edition; `available()` means City, `asn_available()` means ASN, and `status()` reports `asn_available`/`asn_edition`/`asn_build_epoch`/`asn_downloaded_at` next to the City fields. `GET /api/targets/{id}/geo` returns `path_geo()` of the latest ok run: `sources` (local: the run's `src`, or the cached `public_ip()` when that is private; Globalping: `details.probe`/`details.probes[]` coordinates, which `_probe_fields` now records), `hops` and `destination`, each with `geo` or a `note` (`private address`, `not in database`, `no database`), plus `asn` and `as_name` from `_network_fields()`: the number the probe stored (mtr `-z`, Globalping) is kept and the ASN database adds the organisation name, or the number when none was stored; when the stored number disagrees with the database the number stays and `as_name` is null, so the two are never shown mismatched. Globalping probes carry their own `asn`/`network` as the source's network. The response also carries `asn_available`. The destination comes from `_destination()`: `runs.dst_ip` when the run stored one (path, ping, tcp, Globalping ping/http), otherwise the URL's host resolved through `_resolve_cached` (http; a stable made-up address in simulation), and for DNS checks the configured resolver (`role: resolver`) or the first address in `details.answers` (`role: answer`); `role: target` otherwise. An unresolvable far end still yields a destination with `ip: null` and a note so the UI can say why it is missing. Every source carries `evidence` (how it was placed: own address, public address with both addresses named, probe report, simulated) and every `geo` carries `accuracy_km`; the card prints the start's evidence and accuracy under the map (`start-evidence`), popups and the expanded route step print the radius per place. `GET /api/geoip/lookup?q=` (`lookup_query`) locates one address or host name, or `self` through `_monitor_point`, and always answers with `configured`/`available`/`asn_available`/`simulated` plus `asn`/`as_name` so the GeoIP lookup page (`/geoip`, in `NAV`) can explain a missing database and print the network. `enabled` is false without a key and the UI then shows only a pointer to Settings. Simulation mode fabricates locations (`_simulated_route` spreads public hops between monitor and destination) and networks (`_SIM_AS_NAMES` names the numbers the mtr simulator hands out) and skips downloads; tests use `geoip._FORCE_LIVE`, `geoip._TRANSPORT` and patch `geoip._open_reader`. Frontend: `PathMapCard` lazy-loads `PathMap` so Leaflet stays out of every other chunk. `buildStops` returns `stops` (path order; consecutive hops within 0.05° share a stop), `paths` (one polyline per source through the stops), `places` (one labelled marker per coordinate cluster, whether or not its stops are consecutive, because GeoLite2 puts many transit routers in the target's or operator's city and a hop marker would otherwise hide under the target marker; the label lists the hop numbers, e.g. "Target · 7, 8") and `route` (the "Route by place" steps, consecutive hops merged by place name; each step carries `placeId`, its own `lines` and `networks`), plus `networks` (the path's autonomous systems, `networkText(asn, as_name)` = "AS64500 Example Transit GmbH", once each in path order). Stops, places and steps carry `networks` the same way: the step button prints them after the hop numbers (`.route-step-network`, ellipsis past 14rem), the details header and the marker popup list them, and the "Networks" line (`path-networks`) under the route lists the whole path's; when `asn_available` is false that line says the ASN database is still missing and links to Settings. The steps are buttons (`.route-step`, Left/Right/Home/End like `Tabs`): selecting one sets `openStep` (an inline details region) and a `MapFocus {id, seq}` that `PathMap` turns into `setView` + `openPopup` on the marker kept in `markersRef`; a marker click calls `onSelect(placeId)` and opens the first step at that place; a new run (different `routeKey`) clears both. Stops and places also carry `ips` (addresses in path order, once each; a source's `ip` only when it is an address, since simulation stores "simulator"; on a place the destination's address leads); the pill prints `ipText(ips)` ("203.0.113.1 +2") on a second line (`.path-map-marker-ip`) and its `title` lists every address. Route steps carry `ips` too (merged like their `networks`); the step button prints `ipText` after the hop numbers (`.route-step-ip`, `title` lists all), and `.route-step` wraps its pieces (`flex-wrap`, each piece `whitespace-nowrap`) so a phone never breaks an address. Markers are `L.divIcon` pills styled by `.path-map-marker`; tiles are OpenStreetMap, dark themes invert them via `.path-map-dark`; marker colours are read from the CSS variables at draw time and the map only re-fits when the set of places changes. Keep the explanatory footer and HelpTip: the doubling-back line is the database's estimate and confuses readers without them.
- **DNS transport** (`DnsOptions.transport`): `udp` | `tcp` | `dot` | `doh`, plus `resolver_port` (udp/tcp/dot; doh takes the port from its URL) and `verify_tls` (dot/doh). `dot`/`doh` require a resolver (model validator, and the form refuses too); a URL resolver is only valid for `doh` and must be `https://`; `doh_url()` turns a bare host into `https://<host>/dns-query`. Without a resolver `run_dns` keeps the system resolver (`resolve(..., tcp=)`); with one it resolves the server itself (recorded as `details.nameserver`, which `geoip._destination` prefers, taking a URL resolver's host otherwise) and sends one query through `dns.asyncquery` (`udp_with_fallback` notes `details.tcp_fallback`; `tls` with its own non-verifying context when `verify_tls` is off, because dnspython refuses `verify=False` with a server name; `https` with `bootstrap_address`). `details` gains `transport` and `port`; the command reads like dig (`+tcp`, `+tls`, `+https`, `-p`). DoH needs the `h2` package (in `requirements.txt`). The form prints `DNS_TRANSPORT_HELP` under **Transport** (`dns-transport-help`) and, for dot/doh, a **Public resolvers** button group (`ENCRYPTED_DNS_PRESETS` in `TargetForm.tsx`: Cloudflare, Google, Quad9, a host for DoT and a URL for DoH) that fills the resolver. Globalping DNS has `dns_transport` (`udp` | `tcp`), sent as `measurementOptions.protocol`. Tests run local UDP/TCP/TLS DNS servers (`openssl` makes the certificate) and mock `dns.asyncquery.https`.
- **DNS `random_prefix`** queries `<random label>.<name>`; NXDOMAIN/NoAnswer count as a successful lookup when no expected answer is set. **HTTP `tls_info`** stores `details.tls` (`certificate_details()` from the response's ssl object, or a dedicated connection as fallback); `tls_expires_in_days`/`tls_warn_days` stay alongside for the warning.
- **API token**: `MTR_TRACKER_API_TOKEN` enables a middleware in `main.py` that requires a bearer token on `/api` writes; reads stay open. `api.is_authenticated(request)` is the single check (bytes compare, so non-ASCII headers give 401 not 500); with a token configured, `GET /api/settings` returns `redact_settings()` output to unauthenticated callers (mask `********`, last four characters kept for credentials, path and query hidden for the webhook URL) and `GET /api/status` omits `database` (the connection URL without its password, `Database.describe()`) and nulls the database URL and data directory in `environment`. That list (`api._environment`) is the startup configuration as applied, defaults filled in, rendered by the Settings page's **Environment variables** card; the token itself is never echoed (`(set)` or empty). A new `MTR_TRACKER_` variable joins it. `PUT /api/settings` and the notification test run the patch through `strip_masked()` so an echoed mask never overwrites a stored secret. The client stores the token in `localStorage` (`mtr-tracker.token`), sends it on every request, and a 401 dispatches `AUTH_REQUIRED_EVENT`, which the layout turns into a prompt.
- **Unknown `/api/...` paths** return a JSON 404 from the SPA catch-all in `main.py`; never let them fall through to `index.html`.
- **Writes and deletes**: `update_target` rejects explicit nulls with 422 (only `port` may be cleared) and re-checks the tcp port. Deleting a target (single, bulk, or import in replace mode) first calls `Scheduler.cancel(ids)` so a run in flight cannot write against a vanished row; the scheduler also tolerates `db.IntegrityError` (asyncpg's constraint violation) for that case. Run + hops are written inside `db.transaction()` (one pooled connection, one commit or rollback); use it for any multi-statement write, and use only the `tx.*` methods inside the block, never `db.*` (another connection cannot see the uncommitted rows). An insert that needs the new id says `RETURNING id` and goes through `fetchval`; `execute` returns the rows affected.
- **Scheduler details**: `_execute` dispatches to `_execute_path` (local mtr via `_run_local_mtr`, or Globalping mtr/traceroute) or `_execute_probe` (everything else). Notification deliveries are tasks kept in `Scheduler._notify_tasks` and drained by `stop()` (asyncio only holds weak references); `stop()` also awaits the cancelled loop tasks. Route changes are judged only between runs that both reached the destination. `mtr.py` and `probes.py` kill their child process on `CancelledError`. `mtr.min_probe_interval()` is 1 s unless the process is root (mtr refuses shorter `-i` otherwise); `run_mtr` clamps to it and `/api/status` reports it.
- **Database performance**: `runs(started_at)` and `events(run_id)` are indexed (the latter is what the FK `ON DELETE SET NULL` needs); `purge_older_than` deletes in batches of 5000, each its own transaction, with a yield between them; the latest run and the dashboard sparkline are a `CROSS JOIN LATERAL (... ORDER BY started_at DESC, id DESC LIMIT n)` per target over `idx_runs_target_started`, never a `GROUP BY MAX()` join or a `ROW_NUMBER()` window, which read each target's whole history (about 3 s for 40 targets with a month of one-minute runs, and every write in the UI waited for that list). Time buckets are `floor(x / n)::bigint * n`, never `CAST(... AS INTEGER)`: PostgreSQL rounds, and the `::bigint` also types the multiplier parameter (a 32-bit one overflowed for huge ranges). Every `ORDER BY started_at` carries `, id` as the tie-breaker. Keep new hot queries index-backed.
- **Database layer** (`db.py`, asyncpg): write statements with `?` placeholders; `translate()` turns them into `$n` in order (never put a `?` inside a SQL literal; the jsonb `?` operators are refused). `clean()` replaces NUL bytes in text parameters (PostgreSQL text refuses them). `execute()` with no parameters runs the simple-query protocol, which accepts several statements, and therefore refuses a `;`; only `connect()`'s schema runner sends the multi-statement `SCHEMA`. The flags `enabled`, `notify`, `reached` and `route_changed` stay INTEGER 0/1 on purpose: asyncpg's boolean codec accepts only `bool`, so converting them means changing the eight `int(...)` write sites (`_insert_target`, the import update, bulk mute, `update_target`, the three run inserts in `scheduler.py`, `tests/test_routes.py`) and every `= 1` comparison in the same commit. JSON columns stay TEXT (the `json.loads` readers keep their fallbacks; `settings.value` may hold non-JSON). Targets are ordered by `lower(name), name`; the path summary uses `COLLATE "C"` for `MAX(hostname)`/`MAX(asn)` and `h.ip` as the last sort key so the primary address never depends on the server's collation. Remote JSON values bound for text columns (`runs.src`, `dst_ip`) are passed through `str()`. The pool acquires with a 30 s bound and logs exhaustion naming `MTR_TRACKER_DB_POOL_SIZE` (default `max_concurrent_runs + 4`); `executemany` sends 200 rows per round trip inside one transaction (asyncpg cannot be cancelled while transmitting a huge batch); `connect()` retries connection failures until `MTR_TRACKER_DB_CONNECT_TIMEOUT`, bounding each attempt too, and fails at once on a wrong password or database or on a `PermissionError` (asyncpg's client-certificate lookup under HOME; the message names the remedy). The Compose URL carries `?sslmode=disable` because the bundled server speaks no TLS. A `socket.gaierror` while connecting gets the host-networking hint (`_hint`): a Compose service name does not resolve on `network_mode: host`, so the default compose file points the URL at 127.0.0.1 and `docker-compose.bridge.yml` puts the app back on the Compose network; an `InvalidPasswordError` gets the hint that the postgres image applies `POSTGRES_PASSWORD` only when its volume is created (`ALTER USER` afterwards). Run navigation (`prev_run_id`/`next_run_id`) is a keyset on `(started_at, id)`. `db_size_bytes` is `pg_database_size()` (catalogs included, never shrinks after a purge). One app process per database: the scheduler's claim is guarded in memory only.
- **SQLite import** (`migrate.py`): `main.py` calls `auto_import(db, config.sqlite_path)` after `connect()` when `MTR_TRACKER_AUTO_MIGRATE` is on; it imports when the file exists and `db.is_fresh()` (no target, run or event), renames the file and its `-wal`/`-shm` siblings to `.migrated`, warns when PostgreSQL already holds data, and raises `MigrationError` (start aborts, the pool is closed) when the import fails, recording `meta.migration_failed` (path, size and mtime of the file and its `-wal`/`-shm` siblings, message) so the next start fails at once until the file changes; a `SourceChangedError` (rows appeared while reading: an old instance still writing) leaves no marker because the retry is cheap. `import_sqlite()` reads the file read-only (`mode=ro`, never `immutable`) from one `BEGIN` snapshot with keyset pagination, takes `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE` in one PostgreSQL transaction, upserts `meta` and `settings` verbatim (never truncated, replaced keys logged), drops and rebuilds the six indexes around `copy_records_to_table`, copies the columns both sides know (a schema-1 file gets the defaults for `type`, `options`, `notify`, `details`), coerces every value to its column type and counts what changed (`result["coerced"]`: fractional, text, blob, number, nul, invalid_utf8; an infinite number is refused naming the row), skips runs and events older than `retention_days` (the file's value, else the one saved in PostgreSQL, else the default; `--all` keeps them, because the first cleanup tick would purge them anyway) and rows whose parent is missing (events keep their row with the reference cleared), advances the identity sequences past `GREATEST(sqlite_sequence.seq, MAX(id))`, verifies counts, id bounds and the JSON columns byte for byte, then refuses to commit when the source's ids moved meanwhile (a still-running instance). `--replace` truncates the four data tables first. Tests seed legacy files with `LEGACY_SCHEMA_V3`/`V1` at `tmp_path/test.db` before `app_client` starts; `app_client(fresh_database=False)` restarts against the same database.
- **Clearing history**: `Database.delete_runs(target_id, run_ids=, failed_only=)` deletes runs (hops by cascade) and the events whose `run_id` is among them, batched like `purge_older_than`; with neither filter it also deletes the target's events without a run. "Failed" is the runs list's filter (`status != 'ok' OR reached = 0`). `DELETE /api/targets/{id}/runs[?status=failed]` and `POST /api/targets/{id}/runs/delete` (`RunDelete`, ids of other targets are ignored) go through `_delete_history`, which sets `last_status` to `pending` when the latest run was deleted so the next run judges the status again (a pending target raises no "recovered" event). UI: `ClearHistoryDialog` (`components/ClearHistory.tsx`, counts fetched on open) from the target's action menu, and `RunsTable`'s optional `selected`/`onSelect` checkboxes with **Delete N selected** + `ConfirmDialog` in the Runs tab; the selection resets on page, filter or range changes.
- **HTTP keyword regex** (`HttpOptions.keyword_regex`): the keyword becomes a case-insensitive pattern for the `regex` package (Python syntax), searched by `probes.keyword_search` in a worker thread with `KEYWORD_REGEX_TIMEOUT_SEC` (the standard `re` has no timeout, and a catastrophic pattern on a 5 MB body would pin a thread); the model refuses a pattern that does not compile. `details` gains `keyword_regex`, `keyword_match` (the matched text, 200 characters) or `keyword_error`; `CheckDetails` prints **Keyword regex**.
- **HTTP JSON query** (`HttpOptions.json_query`/`json_operator`/`json_expected`): a JSONata expression (the `jsonata-python` package, the language Uptime Kuma uses), evaluated by `probes.evaluate_json_query` in a worker thread with `JSON_QUERY_TIMEOUT_MS`/`JSON_QUERY_MAX_DEPTH` bounds, and compared by `json_condition` (`==`/`!=` on the JSON text with numbers numeric, the order operators numeric only, `contains` case-insensitive; an empty expected value with `==` passes when the result exists and is not false). The model refuses unparseable expressions, a non-`==` condition without an expected value and an order condition with a non-number. `details` carries `json_query`, `json_operator`, `json_expected`, `json_value`, `json_ok` and `json_error`; `CheckDetails` shows them as **JSON query** / **JSON result** and still renders the old `json_path` row of earlier runs. The former option `json_path` (dotted path, comparison inside `json_expected`: `>= 5`, `~text`) is converted by `models.upgrade_http_options`, applied by the model's before-validator, by `_target_out` on every read and by `run_http`, so stored targets need no migration; names JSONata would read as operators get backticks.
- **HTTP probe**: the body is streamed and only `MAX_HTTP_BODY` bytes are kept (`details.truncated` marks a cut); the certificate expiry is read from the response's own TLS connection (`cert_days_from_response`) and only checked when `tls_warn_days > 0`; `details.tls_warn_days` records the threshold the run was judged by. `ping_payload_bytes` makes ping send the same total packet size as mtr. `/api/probe` is limited by `_adhoc_slots` (2 concurrent, 429 after 30 s).
- **Run status**: `runs.status` is `ok` or `error`; `runs.reached` says whether the final hop was the destination. Target `last_status` is `pending | up | degraded | down`; the UI derives `paused` from `enabled = 0`.
- **Scheduling** is fixed-cadence: `next_run_at = started_at + interval_sec`, set when a run is claimed and re-asserted in `finally` (never earlier than now + 1 s). Runs of the same target never overlap because the target id sits in `Scheduler._running`. A 10-probe mtr run takes ~15 s (cycles + ~5 s trailing wait), so the form warns when probes × probe interval + 5 s does not fit the interval.
- **Route change detection** treats unknown hops (`???`) as wildcards (`routes_equivalent`). A run with a different destination IP is reported as a route change with a "now resolves to" message. The stored `runs.route_changed`, the events, notifications and the route-change counts always compare with the previous reached run. Only the latency chart forgets recent routes: `GET /api/targets/{id}/series` runs the range through `route_change_marks(runs, warm, memory)` (`api.py`) with `settings.route_memory_runs` (default 20, 1..500, "Chart route memory (runs)" under Settings → Data & lookups): a flagged run whose route hash appeared among the previous `memory` reached runs gets no marker (`warm` = the reached hashes just before the range, so the first points are judged like the rest), bucketed points are marked when any of their runs is; memory 1 shows every stored change. The suppression is never silent: the response's `route_changes` (`stored`, `marked`, `hidden`, `memory`) lets the target page print "5 route changes hidden by the chart memory (20 runs)" under the chart caption (`route-memory-note`) with a link to `/settings#route-memory`, and the Settings page scrolls to and focuses the field named by the URL hash once its form is loaded. The same rule applies to everything that presents routes: `runs.route_hash` still hashes a silent hop as `*`, so `GET /api/targets/{id}/routes` folds hashes through `_canonical_routes` (one example run's hop sequence per distinct hash, most frequent hash first, wildcard-equivalent hashes attach to it and fill its unknown positions; `routes[].variants` counts the folded hashes), and `GET /api/targets/{id}/hops/summary` folds the `ip IS NULL` group of a hop into the primary address as loss (`hops[].silent_runs`, primary `sent`/`received`/`loss_pct` include those runs, `max_loss_pct` becomes 100) instead of listing "No response" as an alternate. A position that never answered keeps a no-response primary. Rate-limited or deprioritised ICMP on an intermediate router must never look like a reroute or an ECMP alternate.
- **Status history**: `GET /api/targets/{id}/status-history?range=` (`api.status_history`) rebuilds up/degraded/down periods from the target's `down`/`degraded`/`recovered` events (`_event_status`: `details.current`, else the kind; `recovered` = up). Coverage starts at the range start when the target has runs or a status event before it (status = the last earlier event's, else `up`, since a first `up` raises no event), otherwise at its first run in the range; a `pending` start is folded into the first verdict. Periods come newest first, capped at `STATUS_HISTORY_MAX_PERIODS` (500, `truncated`), with `totals` (seconds per status over all of them), `uptime_pct`, `changes` and `paused`. The UI is the **Status history** tab (`components/StatusHistory.tsx`, `data-testid` `status-totals`/`status-period`), offered for every probe type between the path tabs and **Runs**, polled only while shown. `_attach_summaries(db, targets, timeline_sec)` builds the status strip over `timeline_sec` in `TIMELINE_BUCKETS` (48) cells: the dashboard list keeps 86400, `_load_target` passes the page's range; `StatusStrip` takes a `label` and dates its tooltips past a day. `fmtDuration` rounds to its smallest shown unit first (never "6d 24h").

- **Latency units**: every latency or jitter the UI prints goes through the helpers in `utils.ts`, never `${fmtNum(x)} ms`: `fmtMs` ("12.3 ms", from 1000 ms up "1.23 s" / "48.6 s" / "7458465 s", judged after rounding so 999.96 ms never reads "1000.0 ms"), `msParts` (number and unit apart, for the card's big number and `Metric`), `fmtMsCell` (columns headed "(ms)": a bare number, or the value with "s"), `msGroup`/`fmtMsJoin` (values side by side share one " ms" while all are below a second, otherwise each carries its own unit; `trailingUnit: false` for tile subtitles) and `fmtMsTick` (axis ticks). `HeatLegend` switches its title to "(s)" when its maximum reaches a second. Every time axis takes explicit `ticks` from `timeTicks(domain, plotWidth)` (round local-time steps, about one label per 80 px, labels by `fmtAxisTime`: the date alone at local midnight on a multi-day axis) with `minTickGap={4}`: without them Recharts treats every data point as a tick candidate and formatted and measured thousands of labels per render, which froze the target page for seconds on a phone. `fmtTime` uses cached `Intl.DateTimeFormat`s for the same reason. - **Notification cooldown** (`cooldown.py`, does not import `config`): `Scheduler._event` inserts the event, returns when the target is muted or `notify.wanted(settings, kind)` is false (so an alert no channel takes never opens a window), then asks `Scheduler.notify_gate.submit(payload, settings)`. One window per `(target id, category)`, category `status` (down/degraded/recovered) or `route` (route_change), lasting `notify_cooldown_min` minutes from the alert that was sent. Inside it an alert is held (latest kept, count kept, the event row's `details.notification` set to `"held back"`) unless `_escalates` (the last sent severity was not `info` and the new one is higher: degraded -> down; a DOWN after a delivered recovery is held).
