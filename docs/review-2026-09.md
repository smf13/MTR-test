# MTR Tracker: full application review

## Summary

MTR Tracker is a carefully built monitoring application. Its subprocess handling, SQL parameterisation, transactional run writes, cancellation handling, code splitting and documentation discipline are better than is typical for a project of this size. Most of the real risk comes from three areas. First, the default deployment is open: it has no token, listens on all interfaces, has no Host check, and serves raw secrets on reads. Second, the monitor can stop monitoring without saying so: a hung HTTP probe blocks its target, and `/healthz` reports healthy while nothing runs. Third, some checks can report false results, such as Globalping route changes measured from a different probe each run, and IPv6 literals that are never marked as reached. Work that grows with the full history on the hot polling paths will slow the app as retention and target counts grow. Most frontend issues sit in a few shared building blocks: the Modal, the usePoll hook, form labels and light-theme colours. The three high-severity items and the secret-exposure group should be fixed before anyone relies on this in production. Most other fixes are small (S).

## Methodology

**Lanes.** Seven reviewers each covered one area:

- **SEC (security):** authentication, secrets, injection, SSRF, headers, container and supply chain.
- **BE (backend):** scheduler, probes, database layer, API correctness, Globalping, GeoIP.
- **PERF (efficiency):** query plans, polling load, caches, concurrency, render cost.
- **UI (user interface):** visual design, contrast, charts, loading and empty states.
- **UX (usability and accessibility):** interaction flows, keyboard, screen readers, forms, wording.
- **FE (frontend engineering):** hooks, state, API client, component correctness, tests.
- **OPS (operations, tests, docs):** Docker, CI, health checks, logging, dependency pinning, documentation drift.

**Coordination.** Each lane stayed inside its own files and concerns. When a lane noticed something outside its area, it filed a handoff to the owning lane instead of writing a finding, for example SEC to BE on untruncated `json_value`, or UI to UX on the map's `role=img`. A verification lead then checked every finding against the code. It confirmed, downgraded, refuted or merged each one, set the final severity, and turned handoffs that no lane had covered into cross-lane findings (XH-1 to XH-4). Every severity in this report is the verifier's `final_severity`.

**Verification outcomes.**

- 74 lane findings plus 4 handoff findings were verified. None were refuted.
- Three duplicates were merged: PERF-10 into FE-5, UI-5 into FE-1, OPS-6 into SEC-7.
- Two partial overlaps were resolved: the "Clear log" half of UX-15 is covered by FE-8, and the stacked-Escape part of UX-3 is covered by FE-3.
- Six findings were downgraded: SEC-4, BE-3, PERF-1, PERF-3, PERF-8, OPS-2 (see the Appendix).

**Limits.**

- There was no live PostgreSQL server. The pytest suite was not run, and the query-plan claims (PERF-1, PERF-2, PERF-9) come from reading the schema and PG16 planner behaviour. They were not measured with EXPLAIN ANALYZE.
- FastAPI was not installed where the SEC lane ran, so its CSRF and DNS-rebinding behaviour was reasoned from code.
- Some findings were reproduced:
  - BE ran two scripts outside the repo: a slow-drip HTTP server (BE-1) and the simulator with `max_hops=2` (BE-6).
  - FE ran `npm ci`, `tsc` and vitest in a scratch copy (all green) and confirmed FE-3 and FE-4 with throwaway tests.
  - UI computed contrast ratios with a script.
- There was no live rendering, screen-reader run or browser profiling. Theme judgements come from the design tokens and the existing screenshots.

## Top priorities

1. **SEC-1** (M): ship secure defaults. Require or generate an API token, bind to 127.0.0.1 by default, add a Host allow-list, and mask secrets for every reader.
2. **BE-1** (S): give the HTTP probe an overall deadline, plus a per-run safety bound in the scheduler.
3. **BE-2** (M): pin the Globalping vantage point, or skip the route comparison when the probe changes.
4. **SEC-2 and SEC-3** (M + S): mask HTTP probe headers and bodies, and webhook userinfo, for anonymous readers.
5. **OPS-1** (S): add a readiness check that tests the database and scheduler, and point the Docker HEALTHCHECK at it.
6. **BE-3** (S): canonicalise IPv6 literals, or compare addresses by value.
7. **FE-2** (S): clear stale poll data when the target changes, so actions cannot hit the wrong target.
8. **PERF-1 and PERF-7** (S + S): use LATERAL top-N queries for the sparkline and latest run; bound all in-memory caches.
9. **FE-3, UX-2 and UX-3** (M): fix the shared Modal (a stack for Escape and scroll lock, focus management, dirty-form guard).
10. **UI-1 and UI-2** (S): fix light-theme contrast for loss figures and status badges.

## Findings by lane

### Security

**SEC-1: The default deployment has no authentication, listens on all interfaces, and has no Host check**
- Severity: high. Location: `backend/app/main.py:55` (also `api.py:78`, `api.py:226`, `docker-compose.yml:35`).
- What is wrong: the write middleware only exists when `MTR_TRACKER_API_TOKEN` is set, and `is_authenticated` returns true without a token, so `GET /api/settings` returns the raw secrets. Compose publishes 8899 on 0.0.0.0, and nothing validates the Host header.
- Scenario: any host that can reach the port can read the Pushover, Globalping and MaxMind credentials and the full webhook URL, and can create or delete targets. A malicious page the operator visits can DNS-rebind its own name to the monitor and do the same from the browser. Body-less POSTs such as `/run` and `/geoip/update` can also be triggered by a plain cross-site form (CSRF).
- Recommendation: require or generate a token (or refuse to start or warn loudly when none is set and the app is bound publicly), bind Compose to 127.0.0.1, add `TrustedHostMiddleware` with `MTR_TRACKER_ALLOWED_HOSTS`, and always mask secrets on read.
- Effort: M.

**SEC-2: HTTP probe headers and bodies are returned unredacted to anonymous readers**
- Severity: medium. Location: `backend/app/api.py:441` (`_target_out`, `export_targets`; `models.py:36-37`).
- What is wrong: `options.headers` and `options.body` are returned verbatim by the target list and export endpoints, and reads are never token-gated.
- Scenario: with a token set, an operator adds `Authorization: Bearer prod-key`, as the form placeholder suggests. Anyone can then read it through `GET /api/targets` or the export. Credentials in the URL (`https://user:pass@host`) leak the same way.
- Recommendation: mask header values and bodies (and URL userinfo) for unauthenticated callers, run updates and imports through a `strip_masked` equivalent, and document it.
- Effort: M.

**SEC-3: Webhook URL masking leaks the userinfo part**
- Severity: medium. Location: `backend/app/api.py:98`.
- What is wrong: `_mask_url` rebuilds the URL from `netloc`, which includes `user:password@`. A URL with no path and no query is returned unmasked.
- Scenario: a basic-auth relay URL such as `https://user:pw@relay/hook`, or a bare secret host like `https://abc123secret.m.pipedream.net`, is shown in full to anonymous readers.
- Recommendation: rebuild the URL from `hostname` and `port` only, mask the whole value when it carries userinfo, and add tests next to `tests/test_fixes.py:70-78`.
- Effort: S.

**SEC-4: Unrestricted outbound requests (SSRF) through the HTTP, TCP and DNS probes and the webhook test**
- Severity: low (downgraded from medium). Location: `backend/app/probes.py:415`.
- What is wrong: nothing blocks loopback, link-local or RFC 1918 destinations. `json_value` strings are not truncated, and the webhook test echoes 200 bytes of the response body.
- Scenario: whoever has write access creates a target on `http://169.254.169.254/...` with a JSON path, and the cloud credential is stored in run details that anyone can read.
- Recommendation: add an opt-in setting for private targets, always block link-local metadata addresses, cap the `json_value` length, and stop echoing webhook response bodies.
- Effort: M.

**SEC-5: Anonymous `GET /api/geoip/lookup` resolves arbitrary names and can force ip-api.com lookups**
- Severity: low. Location: `backend/app/geoip.py:772`.
- What is wrong: the endpoint is a read, so it is never token-gated. It resolves internal host names with the server's resolver, reveals the public egress IP (`q=self`), and `provider=ip-api` bypasses the operator's off switch.
- Scenario: an anonymous caller maps split-horizon DNS names, and sends chosen addresses to ip-api.com over plain HTTP while using up the shared request budget.
- Recommendation: require the token when one is configured (at least for host names, `self` and `provider=ip-api`), and honour `ip_api_enabled=false` for anonymous callers.
- Effort: S.

**SEC-6: No browser security headers while the token is kept in localStorage**
- Severity: low. Location: `backend/app/main.py:78`.
- What is wrong: there is no CSP, no frame-ancestors or X-Frame-Options, and no nosniff header.
- Scenario: the UI can be framed for clickjacking, and any future XSS could read the bearer token with nothing to contain it.
- Recommendation: add a header middleware that sets CSP (with the inline theme script's hash), `frame-ancestors 'none'`, `nosniff` and `Referrer-Policy`.
- Effort: S.

**SEC-7: Container and supply-chain hardening gaps (canonical entry for dependency and image pinning; absorbs OPS-6)**
- Severity: low. Location: `docker-compose.yml:52` (also `backend/requirements.txt`, `Dockerfile`).
- What is wrong:
  - Compose keeps Docker's default capability set: it adds NET_RAW without `cap_drop: [ALL]`, and sets neither `no-new-privileges` nor `read_only`.
  - Python dependencies are ranges with no lock file, and base images are pinned by tag only.
  - The default database password is `mtr`, and the host override publishes the database on 127.0.0.1:5432.
- Scenario: image builds are not reproducible, and CI can test different dependency versions than the image ships. With the host override, any local user can log in as mtr/mtr and read the stored secrets.
- Recommendation: add `cap_drop: [ALL]` with minimal adds, add `no-new-privileges` (after testing that the file capabilities still work), use a hashed lock file, pin images by digest, and fail when no database password is set (`${MTR_TRACKER_DB_PASSWORD:?...}`).
- Effort: M.

**SEC-8: ip-api.com lookups go over cleartext HTTP**
- Severity: info. Location: `backend/app/ipapi.py:30`.
- What is wrong: this is deliberate and opt-in (the free tier has no TLS), but the Settings text does not say so.
- Scenario: an on-path observer sees every monitored path and can spoof geolocation answers.
- Recommendation: say in the "Use ip-api.com" help text that queries go unencrypted to a third party.
- Effort: S.

### Backend

**BE-1: The HTTP probe has no overall deadline**
- Severity: high. Location: `backend/app/probes.py:354`.
- What is wrong: httpx's timeout applies to each read, not to the whole request. The body loop only ends at 5 MB, and `Scheduler._execute` has no overall bound. A reproduction with a 1 s timeout was still running after 6 s.
- Scenario: an SSE, long-poll or tarpit endpoint keeps the run open forever. The target stays in `_running`, its status freezes (for example at "up"), and it holds one of the 8 semaphore slots. Eight such targets stop all monitoring silently.
- Recommendation: wrap the stream in `asyncio.timeout(timeout)`, bound `_execute` per type, and record an error run when the bound is exceeded.
- Effort: S.

**BE-2: Globalping mtr and traceroute compare routes from different remote probes**
- Severity: high. Location: `backend/app/scheduler.py:274` (also `globalping.py:94-97`).
- What is wrong: each measurement picks a new probe from the location pool, and the scheduler compares the result with the previous reached run without checking that the vantage point is the same. The simulator always uses the same probe, so tests cannot see this.
- Scenario: a target with location "world" or "Germany" is measured from Frankfurt, then Berlin. Almost every run is stored as a route change and sends a notification, and the latency series mixes continents.
- Recommendation: store the measurement id and reuse it as `locations` on the next request, or skip the comparison (or start a new baseline) when the probe identity changes. Make the simulator vary the probe, and update the docs.
- Effort: M.

**BE-3: A non-canonical IPv6 literal is never "reached"**
- Severity: medium (downgraded from high). Location: `backend/app/resolver.py:25`.
- What is wrong: `resolve_host` returns the user's text unchanged, and `scheduler.py:261` compares it as a string with mtr's canonical output. The same comparison appears in `api.py:1253` and `geoip.py:709`.
- Scenario: the host `2001:4860:4860:0:0:0:0:8888` is shown as permanently DOWN with 100% loss and sends DOWN notifications.
- Recommendation: canonicalise with `str(ipaddress.ip_address(host))` in the resolver and the validator, and add a regression test.
- Effort: S.

**BE-4: Bulk resume resets `last_status` on targets that were already enabled**
- Severity: low. Location: `backend/app/api.py:485`.
- What is wrong: the UPDATE applies to every selected id, while `update_target` resets the status only on a real paused-to-enabled transition.
- Scenario: resuming everything sends a duplicate DOWN notification for an ongoing outage and loses the "recovered" event.
- Recommendation: use `CASE WHEN enabled = 0 THEN 'pending' ELSE last_status END`, and likewise for `next_run_at`.
- Effort: S.

**BE-5: A run in flight overwrites `next_run_at` after an edit**
- Severity: low. Location: `backend/app/scheduler.py:187`.
- What is wrong: the `finally` block writes `started + interval` from the snapshot taken at run start, which overwrites the `next_run_at = now` set by the edit.
- Scenario: after changing the host of a 3600 s target while it runs, the corrected target does not run for up to an hour.
- Recommendation: only move `next_run_at` forward (a conditional UPDATE), or skip the write when `updated_at` is later than the run's start.
- Effort: S.

**BE-6: The simulated mtr crashes at random when `max_hops` is 1 or 2**
- Severity: low. Location: `backend/app/mtr.py:313`.
- What is wrong: the `randint` bounds assume at least 4 path entries. Across 400 runs, about 7% failed.
- Scenario: simulation mode, or a host without mtr (which falls back to the simulator), produces "internal error" runs and DOWN alerts.
- Recommendation: guard the route-flip and incident branches on the path length, or clamp the indices.
- Effort: S.

**BE-7: `parse_range` has no upper bound**
- Severity: low. Location: `backend/app/api.py:43`.
- What is wrong: the regex branch accepts `0s` and huge values. `datetime.fromtimestamp` raises, and the bucket arithmetic can overflow int64.
- Scenario: `?range=1000000w` returns a 500 instead of a 400.
- Recommendation: clamp the range to 60 s through 3650 d, return 400 outside it, and apply one minimum to both parsing paths.
- Effort: S.

**BE-8: Hop summary, hop history and routes include unreached runs padded to `max_hops`**
- Severity: low. Location: `backend/app/api.py:817`.
- What is wrong: these queries filter only `status = 'ok'`, not `reached`, and unreached runs are padded with unknown hops up to `max_hops`.
- Scenario: a 5-minute outage adds hops 11 to 30 as "no response" entries, makes the heatmap 30 rows tall, and adds a pseudo-route.
- Recommendation: restrict these queries to reached runs, or trim trailing unknown hops. Label outages in `/routes` as outages, not route variants.
- Effort: M.

**BE-9: The Globalping poll does not wrap JSON or shape errors**
- Severity: low. Location: `backend/app/globalping.py:195`.
- What is wrong: `poll.json()` has no try, and `run_globalping_path` catches only `GlobalpingError`.
- Scenario: an HTML 200 page from a proxy is stored as "internal error: Expecting value...".
- Recommendation: catch `ValueError` and `AttributeError`, and raise `GlobalpingError` with a readable message.
- Effort: S.

### Efficiency

**PERF-1: The dashboard and target page scan each target's whole run history for sparklines and the latest run**
- Severity: medium (downgraded from high). Location: `backend/app/api.py:322`.
- What is wrong: the `GROUP BY MAX(started_at)` join and the partitioned `ROW_NUMBER` have no time bound. PG16 has no loose index scan, and the index lacks `id` for the tie-breaker. Both endpoints are polled every 10 s.
- Scenario: 50 targets at 1 run per minute with 30-day retention means about 2 M rows read twice per poll per open tab, holding pool connections the scheduler needs.
- Recommendation: use a LATERAL top-N per target (LIMIT 60 and LIMIT 1), and extend the index to `(target_id, started_at DESC, id DESC)`.
- Effort: S.

**PERF-2: The hop summary aggregates every hop row in the range and is polled for hidden tabs**
- Severity: medium. Location: `frontend/src/pages/TargetDetail.tsx:64`.
- What is wrong: history, summary, runs, events and routes are all polled whichever tab is active, and the hop summary heap-fetches every hop row in the range.
- Scenario: at a 30-day range, about 1.3 M hop rows are aggregated every 30 s while the user reads the Runs tab.
- Recommendation: poll only the active tab, slow the polling for long ranges, or cache by the latest run id. Consider an hourly rollup table.
- Effort: M.

**PERF-3: `/api/status` runs `COUNT(*)` over all runs, and Settings polls it twice**
- Severity: low (downgraded from medium). Location: `backend/app/api.py:200`.
- What is wrong: an exact count runs every 15 s from Layout, and Settings adds a second 10 s poller.
- Scenario: overhead that grows with history for a number shown only as a statistic.
- Recommendation: use the `pg_class.reltuples` estimate or a cached count, and drop the duplicate poller.
- Effort: S.

**PERF-4: The target endpoint loads every run in the range into Python every 10 s**
- Severity: medium. Location: `backend/app/api.py:511`.
- What is wrong: `_range_stats` fetches every row in the range and sorts it in Python. The target poll runs at a fixed 10000 ms instead of `pollMs`.
- Scenario: at 30 days on a 1-minute target, 43k rows are decoded per poll per viewer, and that event-loop CPU delays the scheduler.
- Recommendation: compute the statistics in one SQL aggregate with `percentile_cont`, and poll at `pollMs`.
- Effort: S.

**PERF-5: The route timeline renders one DOM node per segment with no bound**
- Severity: medium. Location: `frontend/src/components/Visuals.tsx:414`.
- What is wrong: `get_routes` returns every hash change, and each segment is a div whose hover state lives in React.
- Scenario: an ECMP path over 30 days produces about 43k divs and a multi-MB payload, and every hover re-renders all of them.
- Recommendation: merge segments server-side to display resolution (500 slots or fewer), or draw on canvas or SVG, and drive the hover with CSS.
- Effort: M.

**PERF-6: A 1 s `useNow` tick re-renders whole pages, including three charts, with no memoisation**
- Severity: medium. Location: `frontend/src/pages/TargetDetail.tsx:40`.
- What is wrong: TargetDetail, Dashboard and Events tick every second, and no component uses `React.memo`.
- Scenario: a wall display re-renders three Recharts charts, the route strip and 50 dashboard cards every second, which drains CPU and battery.
- Recommendation: move relative times into a small `<RelTime>` component with its own tick, memoise the charts and stabilise their callbacks.
- Effort: M.

**PERF-7: The GeoIP, DNS and ip-api caches never evict**
- Severity: medium. Location: `backend/app/geoip.py:118`.
- What is wrong: five module-level dicts are evicted only when an expired key is read again, and the unauthenticated lookup endpoint can add arbitrary keys.
- Scenario: a script calling `lookup?q=<random>` grows memory until the container is OOM-killed, taking the scheduler down with it.
- Recommendation: use bounded TTL/LRU caches (about 10k entries), and optionally rate-limit the lookup endpoint.
- Effort: S.

**PERF-8: Scheduler queue lateness is invisible**
- Severity: low (downgraded from medium). Location: `backend/app/scheduler.py:155`.
- What is wrong: `started` is taken after the semaphore is acquired, and no lateness metric exists. The default of 8 concurrent runs caps throughput at about 32 mtr runs per minute.
- Scenario: 50 mtr targets at 60 s actually run about every 94 s, with no sign in the UI or logs.
- Recommendation: record the claim-versus-due lag, expose it in `/api/status` and log a warning; consider a higher default.
- Effort: S.

**PERF-9: The "previous reached run" lookup walks the whole history when a target never reaches its destination**
- Severity: low. Location: `backend/app/scheduler.py:267`.
- What is wrong: `status` and `reached` are checked on every heap row, and the lookup runs even when the current run did not reach.
- Scenario: a target behind a firewall that drops ICMP scans all of its runs on every run and on every series poll.
- Recommendation: add a partial index `WHERE status = 'ok' AND reached = 1`, and skip the lookup unless the run reached.
- Effort: S.

**PERF-11: A new httpx client and SSL context are built for every request**
- Severity: low. Location: `backend/app/probes.py:354` (also `ipapi.py:169`, `globalping.py:152`, `geoip.py:457`, `notify.py:29`).
- What is wrong: loading the certificate bundle blocks the event loop each time (not measured).
- Scenario: many short-interval HTTP and Globalping targets cause recurring event-loop stalls.
- Recommendation: build the SSL contexts once, and reuse long-lived clients for the API integrations.
- Effort: S.

**PERF-12: Shielded reverse-DNS lookups keep executor threads busy and can starve forward resolution**
- Severity: low. Location: `backend/app/resolver.py:64`.
- What is wrong: `getnameinfo` keeps running after its `wait_for` gives up, in the same executor that `getaddrinfo` uses.
- Scenario: a slow PTR resolver makes `resolve_host` exceed 8 s, which is recorded as "DNS lookup timed out", a false DOWN.
- Recommendation: give reverse DNS a separate bounded executor or semaphore, or use an async resolver.
- Effort: M.

### User interface

**UI-1: Loss figures in `lossColor` are almost unreadable in the light theme**
- Severity: medium. Location: `frontend/src/utils.ts:86`.
- What is wrong: translucent lime, amber and green are used as text colours, giving 1.4 to 2.7:1 contrast on white.
- Scenario: "2.0%" loss in the hop table pill and on dashboard cards, the number an engineer looks for first, is the hardest one to read.
- Recommendation: add a theme-aware `lossTextColor` at 4.5:1 or better, and keep `lossColor` for fills.
- Effort: S.

**UI-2: Status badges and status-coloured text fail WCAG AA in the light theme**
- Severity: medium. Location: `frontend/src/components/StatusBadge.tsx:5`.
- What is wrong: degraded text on its soft background is 2.86:1, up is 3.0:1, and `text-degraded` on white is 3.19:1.
- Scenario: the main state signal on every card and row sits below AA.
- Recommendation: darken the light-theme foregrounds, or add `--*-fg` tokens for text.
- Effort: S.

**UI-3: The multi-target chart palette is illegible on light, and colours are keyed by target id**
- Severity: medium. Location: `frontend/src/utils.ts:119`.
- What is wrong: `seriesColor(t.id)` repeats every 12 ids, and the lime and yellow hues are about 1.5:1 on white. Routes past 12 reuse colours.
- Scenario: two targets can get the same line colour, some lines are invisible in light mode, and route 13 looks like route A.
- Recommendation: assign colours by position in the list, use a darker light-theme palette, and show an "other" fill past 12 routes.
- Effort: S.

**UI-4: Map marker pills are white text on light fills in the dark themes**
- Severity: low. Location: `frontend/src/index.css:213`.
- What is wrong: contrast is 2.1 to 2.6:1 at 10 to 11 px, in the default dark theme.
- Scenario: the hop-order labels on the map are hard to read.
- Recommendation: use `--accent-fg` or a dark text colour on light fills.
- Effort: S.

**UI-6: Heatmap tooltips are clipped by the scroll container and can sit at a negative left**
- Severity: low. Location: `frontend/src/components/HopHeatmap.tsx:57` (also HourlyHeatmap).
- What is wrong: the tooltip is absolute inside an `overflow-x-auto` box, and `left` can go below zero.
- Scenario: the tooltip for the destination row is cut off, and a scrollbar flickers as the mouse moves.
- Recommendation: portal the tooltip with fixed positioning, or flip it above the cell, and clamp `left` to 0 or more.
- Effort: S.

**UI-7: Stat tiles colour severity inconsistently**
- Severity: low. Location: `frontend/src/pages/TargetDetail.tsx:230`.
- What is wrong: the uptime tone is a two-way ternary. 0% uptime is amber, and the dash placeholder shown with no data is green.
- Scenario: the tiles contradict the red Down badge beside the title.
- Recommendation: use three bands, no tone for null, and the same banding on the Loss tile.
- Effort: S.

**UI-8: Dashboard table actions are off-screen at laptop widths**
- Severity: low. Location: `frontend/src/pages/Dashboard.tsx:412`.
- What is wrong: 14 columns with no sticky actions column.
- Scenario: the user must scroll each table horizontally to reach Run now.
- Recommendation: make the actions column sticky, or move the actions next to the name.
- Effort: S.

**UI-9: The hour-by-day heatmap in Loss mode cannot tell "no response" from high loss**
- Severity: low. Location: `frontend/src/components/Visuals.tsx:363`.
- What is wrong: a fully failed bucket uses the same red as 60%+ loss, and the legend omits the "No response" swatch in Loss mode.
- Scenario: an outage looks the same as 65% loss, while the HelpTip says red means an outage.
- Recommendation: give failed buckets a distinct treatment, add the legend swatch, and fix the HelpTip wording.
- Effort: S.

**UI-10: Small legend and encoding inconsistencies**
- Severity: info. Location: `frontend/src/pages/TargetDetail.tsx:424`.
- What is wrong: the route-change legend swatch is solid while the chart line is dashed, and it shares the jitter colour. The percentiles use status colours, and the overview chart's linear axis flattens every target under one outlier.
- Recommendation: draw the swatch dashed with a dedicated `--chart-route` token, use neutral percentile shades, and offer a log scale option.
- Effort: S.

### Usability and accessibility

**UX-1: The UI never says why a target is degraded**
- Severity: medium. Location: `backend/app/scheduler.py:358`.
- What is wrong: `_apply_status` returns early when the status is unchanged, and warnings live only in the transition event. The tiles compare range averages with the thresholds.
- Scenario: a target is degraded by loss, but the only reason shown is the stale "latency 230 ms" message from an old event.
- Recommendation: persist the current reason, show it beside the badge, emit an event when the reason changes, and base the tile highlights on the latest run.
- Effort: M.

**UX-2: Modal dialogs do not manage focus**

## Cross-cutting themes

1. **Reads expose secrets by default.** The token guards writes only. Raw settings (without a token), HTTP probe headers and bodies, webhook userinfo, GeoIP lookups and run details are all readable anonymously, and there is no Host check against DNS rebinding (SEC-1, SEC-2, SEC-3, SEC-5, XH-1, XH-2).
2. **Failures are silent and state goes stale.** A hung probe freezes a target, the health check stays green, the UI shows stale data or "Loading…" on errors, data from the previous target lingers, degraded reasons go stale, and scheduler lateness is invisible (BE-1, OPS-1, OPS-4, FE-1, FE-2, FE-4, UX-1, PERF-8).
3. **Hot paths do work proportional to the whole history.** Unbounded scans, Python-side statistics, polling for hidden tabs, unbounded route segments, unbounded caches and unbounded range parameters (PERF-1, PERF-2, PERF-3, PERF-4, PERF-5, PERF-7, BE-7).
4. **Equality assumptions produce false signals.** Addresses are compared as strings, the Globalping vantage point is never pinned, and padded unreached runs are mixed into aggregates. All of these contradict CLAUDE.md's rule that routing noise must never look like a reroute (BE-2, BE-3, BE-8).
5. **Accessibility debt sits in shared building blocks.** The Modal, form labels, toasts, pointer-only drill-downs, tab patterns and light-theme contrast (UX-2, UX-3, UX-4, UX-5, UX-7, UX-12, FE-3, UI-1, UI-2, UI-3, XH-3).
6. **Tests and CI lag the documented rules.** The simulator hides real-world variance, the frontend primitives have no tests, the Python 3.11 and PostgreSQL 13 promises are never checked, and there is no container smoke run (FE-7, FE-10, OPS-7, BE-2, BE-6).

## Strengths

- **No command or SQL injection path.** Subprocesses use argv lists, mtr and ping receive only resolved IP literals, and host values starting with `-` are rejected. All SQL is parameterised, and `translate()` refuses the jsonb `?` operators.
- **Careful secret handling within its scope.** Token comparison is constant-time on bytes, echoed masks cannot overwrite stored secrets, and `describe()` never includes the database password. Leaflet HTML is escaped, and there is no `dangerouslySetInnerHTML`.
- **Safe file and archive handling.** GeoLite2 archives are extracted member by member, verified and replaced atomically. Static serving is protected against path traversal.
- **Robust transactions and cancellation.** Runs and hops are written in one transaction, child processes are killed on cancel, deletes wait for in-flight runs, and the scheduler and cleanup loops survive errors.
- **Correct route-change logic across outages.** Routes are compared only between reached runs, and unknown hops act as wildcards.
- **Defensive database layer.** NUL-byte cleaning, bounded pool acquire, chunked `executemany`, connection retries with configuration hints, and a batched purge backed by an index.
- **Well-behaved ip-api.com client.** It batches, keeps a strict request budget, and handles pauses correctly.
- **Careful SQLite migration.** It reads a snapshot, locks the target tables, verifies byte for byte, and refuses to commit if the source changed.
- **Sound frontend architecture.** Strict TypeScript that type-checks cleanly, correct generation handling in usePoll, disciplined code splitting (Recharts and Leaflet stay out of the first paint), and a well-structured theme token system.
- **Good interaction details.** ActionMenu, Popover and route steps have complete keyboard support. Destructive actions are confirmed, the form warns when a schedule cannot fit, and chart route-memory suppression is never silent.
- **Careful container setup.** tini as PID 1, setpriv to uid 1000, file capabilities instead of root, a healthy-gated database dependency, and an unpublished database port by default.
- **Docs closely match the code.** Every environment variable and route is documented, and the interface labels exist in the source.
- **Realistic backend tests.** They run against a real PostgreSQL with a fresh database per test and MockTransports for every external service.
